## 프롬프트 원문

euidaeguard-backend의 RAG가 **온보딩에서 고른 업종에 맞는 근거만 쓰도록** 만들어줘.
지금은 업종 정보가 메타데이터로만 있고 실제 검색에는 쓰이지 않는다.

### 현재 상태 (이미 되어 있는 것, 다시 만들지 말 것)

- `app/rag/ingest.py`
  - `knowledge-sources/`를 재귀 순회하며 `.md`만 인덱싱한다(`_` 로 시작하는 폴더는 제외).
    PDF 로더는 md 전환과 함께 제거했다.
  - `SOURCE_REGISTRY`가 문서별로 `title` / `source_type` / `industries` / `indexed` / `reason`을 관리한다.
  - `industries`에는 이미 업종 ID가 들어 있다. 예: 마트계산원 매뉴얼은 `("convenience_store",)`,
    식품등의 표시기준은 `("convenience_store", "restaurant_cafe", "online_shopping")`,
    법령·고시류는 전 업종(`("*",)`).
  - 각 청크 metadata에 `documentTitle`, `sourceType`, `section`, `page`, `industries`, `sourcePath`가 실린다.
  - 청크 총 553개(문서 5건 + 제외 2건).
- `app/rag/retrieve.py`
  - `retrieve_relevant_chunks(query_text, top_k=5, pinned_sections=())`
  - `pinned_sections`로 지정한 섹션을 유사도 검색 결과 앞에 강제로 붙인다.
  - 문서당 최대 2청크(`MAX_PER_DOCUMENT`)로 한 문서의 독식을 막는다.
- `app/graph/recommendation_graph.py`
  - `PINNED_SECTIONS: dict[tuple[industryId, problemType], tuple[str, ...]]`가
    `(convenience_store, refund_exchange) → ("식료품(19개 업종)", "[별표 1]")` 식으로 조항을 고정한다.
  - `_pinned_sections(state)`가 `profile.industryId` + `intake.problemTypes`로 이 표를 찾는다.
- 업종 ID 목록은 `euidaeguard-web/src/lib/mock/onboardingOptions.ts`의 `INDUSTRIES`:
  `convenience_store`, `online_shopping`, `restaurant_cafe`, `hospital`,
  `education`, `real_estate`, `lodging_travel`, `professional_service`.

1. ~~`retrieve_relevant_chunks`에 업종 필터를 추가해줘.~~ **(2026-09-15 구현 완료)**
   - `_matches_industry()`가 청크의 `industries`를 보고 `["*"]` 또는 현재 업종 ID일 때만 통과시킨다.
   - `retrieve_node`가 `state["profile"].industryId`를 넘긴다. pinned/유사도 양쪽에 모두 적용된다.
   - 업종을 모르거나 `industries`가 비었으면 통과시키는 쪽으로 정해 두었다.
   - 남은 일: 아래 2~5번.
2. 필터 때문에 근거가 0건이 되는 경우의 동작을 정해줘.
   - 전 업종 문서(`["*"]`)만으로 재검색할지, 필터를 풀고 재검색할지, 그대로 0건으로 두고

   - 업종별로 필요한 자료가 무엇인지(예: 온라인 쇼핑몰이면 전자상거래법상 청약철회) 목록으로 제시해줘.
4. `[별표4][별표3] 품목별 품질보증기간 및 부품보유기간` 문서의 처리를 다시 정해줘.
   - 지금은 대응 업종이 없어서 `indexed=False`로 빼 두었다. 업종 필터가 생기면
     적절한 `industries` 값을 주고 다시 넣을 수 있는지 검토해줘.
5. 검증까지 해줘.
   - 업종별로 대표 질의를 3개씩 만들어 필터 적용 전/후 검색 결과를 비교한 표를 보여줘.
   - 편의점 시나리오(요구르트 변질 환불)가 필터 적용 후에도 별표Ⅱ 식료품 조항을 계속 인용하는지 확인해줘.
     (시행령 별표1 일반기준은 md 전환 때 폴더에서 빠졌다 — `knowledge-sources/README.md`의 "빠진 자료" 참고.
     다시 넣을지부터 정해야 한다.)

### 지켜야 할 것

- 지식베이스를 다시 임베딩해야 하면 먼저 `build_documents()`만 돌려 청크 구성을 확인한 뒤 진행해줘.
  (`app/rag/vector_store.json`은 24MB, 재생성에 OpenAI 임베딩 비용이 든다)
- 근거가 없는 내용을 모델이 지어내지 않도록 하는 게 이 기능의 목적이다.
  업종 필터가 오히려 필요한 근거를 가려버리면 실패다. 재현율을 먼저 보고 정밀도를 나중에 보자.
- `knowledge-sources/README.md`의 인덱싱 정책 표도 같이 갱신해줘.

## 참고: 이 작업이 필요한 이유

`SOURCE_REGISTRY`에 업종 정보를 넣어 두기만 하고 검색에는 쓰지 않는 상태다.
편의점용 실무 매뉴얼이 병원·부동산 업종 상담에도 그대로 검색되고, 반대로 업종별로
꼭 필요한 근거(전자상거래법상 청약철회 등)는 아예 자료가 없다.
온보딩에서 업종을 고르게 해 놓고 그 선택이 답변 품질에 반영되지 않으면 온보딩 자체가 무의미해진다.
