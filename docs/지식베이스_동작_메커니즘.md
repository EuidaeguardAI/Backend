새 시나리오(다른 컴플레인 유형·다른 업종)를 붙일 때 **어디를 건드려야 하는지** 찾는 용도로 쓴다.

기준 시점: 2026-09-17 / 인덱스 553청크 / 문서 5건(+제외 2건)
원본 자료는 전부 Markdown이다. PDF·DOCX는 더 이상 인덱싱하지 않는다(2-2 참고).

## 1. 한눈에 보는 흐름

```
[사전 작업: 문서가 바뀔 때만]
knowledge-sources/*.md  →  ingest.py  →  app/rag/vector_store.json (24MB, 553청크)
   Markdown 원본             레지스트리 조회 → 헤딩 경로·원문 쪽수 인식
                             → 표 보존 청킹 → 잔조각 병합 → 문맥 헤더 부착 → OpenAI 임베딩

[런타임: 발화 1건마다]
POST /analyze
   └ recommendation_graph
       ├ (위협 키워드/반복 폭언 감지) → fixed_safety → END      ← RAG 안 탐
       └ retrieve → generate → END
            retrieve : 업종 필터 → 조항 고정 → 유사도 검색 → 문서당 상한
            generate : 근거 블록 조립 → LLM 구조화 출력 → citations
```

핵심은 **런타임에는 문서를 읽지 않는다**는 점이다. 런타임이 보는 것은 `vector_store.json` 하나뿐이고,
원본 Markdown을 바꾸든 새 파일을 넣든 `python -m app.rag.ingest`를 다시 돌리기 전까지는 아무 영향이 없다.

## 2. 사전 작업 — 문서가 청크가 되기까지

파일: [app/rag/ingest.py](../app/rag/ingest.py)

### 2-1. 레지스트리 조회 (`SOURCE_REGISTRY`)

`knowledge-sources/`를 재귀 순회하면서 `.md`를 찾고, 상대경로를 키로 정책을 찾는다.
`.md`가 아닌 파일은 `[건너뜀]`으로 찍고 넘어간다. `_` 로 시작하는 하위 폴더(`_archive/` — 변환 전 원본)도 통째로 건너뛴다.
파일명은 원본 자료의 이름을 그대로 쓴다. 레지스트리 키가 그 파일명이므로, 파일명을 바꾸면 키도 같이 바꾼다.

| 필드 | 뜻 | 어디에 쓰이나 |
|---|---|---|
| `title` | 문서 제목 | 그대로 `citations[].label`이 된다. **사용자에게 보이는 이름** |
| `source_type` | `standard` / `notice` / `law` / `guide` / `manual` | 프롬프트에 "공식 고시" vs "사내 매뉴얼(법령 아님)"로 표기됨 |
| `industries` | 업종 ID 튜플, `("*",)`는 전 업종 | 검색 시 업종 필터의 기준 |
| `indexed` | 인덱싱 여부 | `False`면 통째로 제외 |
| `reason` | 제외 사유 | ingest 실행 로그에 출력 |

레지스트리에 없는 파일도 인덱싱되지만 `[경고]`를 찍고 `title=파일명`, `source_type="unclassified"`로 들어간다.
citations에 파일명이 그대로 노출되므로 **새 자료를 넣으면 반드시 레지스트리에 등록**한다.
반대로 레지스트리에만 있고 파일이 없으면 역시 `[경고]`를 찍는다 — 파일을 지우거나 이름을 바꾸고
레지스트리를 안 고친 경우다. 그대로 두면 그 문서를 겨냥한 `PINNED_SECTIONS`가 조용히 아무것도 못 찾는다.

현재 구성:

| 문서 | 청크 | source_type | industries |
|---|---|---|---|
| 소비자분쟁해결기준 [별표Ⅰ][별표Ⅱ] | 212 | standard | `*` |
| 식품등의 표시기준 (식약처 고시) | 241 | notice | convenience_store, restaurant_cafe, online_shopping |
| 고객응대근로자 건강보호 가이드 | 73 | guide | `*` |
| 고객응대근로자 건강보호 업종별 매뉴얼 - 마트계산원 | 23 | guide | convenience_store |
| 소비자분쟁해결기준 (고시 본문) | 4 | standard | `*` |

제외: 별표Ⅲ/Ⅳ(공산품 품질보증기간 — 대응 업종 없음), README.
빠진 자료(시행령 [별표1] 일반기준, 편의점 실무 매뉴얼)는 [knowledge-sources/README.md](../knowledge-sources/README.md) 참고.

### 2-2. Markdown 로더

**지원 형식은 `.md` 하나다.** PDF 로더는 md 전환과 함께 걷어냈다(`pypdf` 의존성도 제거).
PDF 텍스트 추출은 표를 줄바꿈된 평문으로 뭉개서 "분쟁유형 / 해결기준 / 비고"의 열 대응이 사라졌는데,
Markdown 표는 이 대응이 그대로 남아 LLM이 행·열을 읽을 수 있다.
그래서 자료를 넣을 때 사람이 먼저 Markdown으로 변환하고, 변환 전 원본을 남기려면 `_archive/`에 둔다.

로더가 하는 일은 세 가지다.

**① 헤딩 경로(breadcrumb)** — `#`~`######`를 섹션 경계로 삼되, 직전 헤딩 하나가 아니라 **경로 전체**를 남긴다.
`"1) 완제품"`이나 `"가) 문구 게시 장소"`는 그 자체로는 어느 품목 이야기인지 알 수 없고, 그대로
`citations[].section`에 실려 사용자에게도 그렇게 보인다. 경로를 남기면 `"5. 가전제품 ... > 1) 완제품"`이 된다.
한 마디가 40자를 넘으면 줄여서 담는다 — 변환본에는 원문에서 줄바꿈된 항목이 그대로 헤딩이 된 경우가
많아서(`"다. “제조연월일”이라 함은 포장을 제외한 더 이상의 제조나 가공이"`) 위치 표시가 문장 중간에서 끊긴다.
본문에는 온전한 헤딩 줄이 남으므로 LLM이 읽는 내용은 줄지 않는다.

**② 원문 쪽 표시 분리** — 변환본은 원문 쪽을 `## 원문 8쪽` 또는 `<!-- 원문 PDF 8쪽 -->`로 남겨 둔다.
이건 목차가 아니라 위치 정보다. 헤딩으로 취급하면 `"2. 식료품(19개 업종)"` 같은 진짜 제목을 덮어써서
근거 위치가 `"원문 8쪽"`이 돼버린다. 그래서 제목 대신 `page` 메타데이터로 뺀다.

**③ 표 보존 청킹** — 아래 2-3 참고.

> PDF 시절의 `SECTION_PATTERNS`(정규식으로 `제N조(제목)`·`<별표 Ⅱ>`를 찾아내던 것)는 없앴다.
> Markdown에서는 문서의 목차 체계가 이미 `#` 단계로 표현돼 있어서, 문서마다 패턴을 추가할 일이 없다.
> **새 자료를 넣을 때 헤딩이 제대로 잡혔는지만 확인하면 된다**(6-C 참고).

### 2-3. 표를 살려서 자르기

표를 일반 텍스트로 취급하면 700자에서 행 한가운데가 잘려서, 뒤 청크는 헤더행 없이
`| 2) 부패, 변질 | o 제품교환 또는 구입가 환급 |`만 남는다. 열 이름이 사라지면 LLM은 두 번째 칸이
해결기준인지 비고인지 알 수 없다. 그래서 표는 따로 다룬다.

- 행 경계에서만 자른다. 자를 때마다 **헤더행(+구분행)을 각 조각 앞에 다시 붙인다.**
- 표 바로 위 도입부(200자 이내)도 함께 붙인다. 별표Ⅱ는 품종 목록을 표 위에 굵은 글씨로 적어 두는데,
  `"요구르트"`·`"빵"` 같은 실제 품목명은 표 본문이 아니라 **이 줄에만** 나온다. 끊기면 검색 단서가 사라진다.
- 행 하나가 이미 700자를 넘으면(별표Ⅱ 공산품 행은 1,600자가 넘는다) 자르지 않고 통째로 둔다.
  행 중간을 자르면 표가 아니라 부서진 문자열이 된다.

원문 쪽 경계의 수평선(`---`)은 내용이 없으므로 버린다.

### 2-4. 청킹

`RecursiveCharacterTextSplitter(chunk_size=700, chunk_overlap=120)`.
구분자 우선순위는 `빈 줄 → 줄바꿈 → ". " → "다. " → 공백`.

> 이전 구현은 빈 줄(`\n{2,}`)로만 잘랐는데, PDF 추출 텍스트에는 빈 줄이 거의 없어서
> **페이지 하나가 통째로 청크 하나**가 됐다(137페이지 문서 → 700자 초과 청크 88개).
> 지금은 700자 초과 청크가 0개다.

### 2-5. 문맥 헤더 부착 (`contextualize`)

임베딩 직전, 청크 본문 앞에 `[문서명 · 섹션]` 한 줄을 붙인다.

```
[소비자분쟁해결기준 [별표Ⅰ] 대상품목 · [별표Ⅱ] 품목별 해결기준 · 품목별 해결기준 > 2. 식료품(19개 업종)]
**청량음료, 과자류, 빙과류, 낙농제품류, 통조림류, 제빵류, ...**
| 분 쟁 유 형 | 해 결 기 준 | 비 고 |
| --- | --- | --- |
| 1) 함량, 용량부족<br>2) 부패, 변질<br>... | o 제품교환 또는 구입가 환급<br>... | ... |
```

법령 표 본문은 "제품교환 또는 구입가 환급"처럼 건조해서 직원의 실제 발화와 벡터 거리가 멀다.
문서명·섹션을 본문에 포함시키면 이 간극이 줄어든다.

### 2-6. 최종 청크 메타데이터

```python
{
  "documentTitle": "소비자분쟁해결기준 [별표Ⅰ] 대상품목 · [별표Ⅱ] 품목별 해결기준",
  "sourceType":    "standard",
  "section":       "품목별 해결기준 > 2. 식료품(19개 업종)",   # 헤딩 경로. 한 마디는 40자까지
  "page":          8,               # 변환본의 "원문 N쪽" 표시. 표시가 없는 문서는 None
  "industries":    ["*"],
  "sourcePath":    "[별표1] [별표 2] 품목별_해결기준_2024-12-27.md",
}
```

## 3. 런타임 — 근거를 고르는 4단계

파일: [app/rag/retrieve.py](../app/rag/retrieve.py)

```python
retrieve_relevant_chunks(query_text, top_k=5, pinned_sections=(), industry_id=None)
```

### 단계 1. 업종 필터 (`_matches_industry`)

청크의 `industries`가 `["*"]`이거나 현재 업종 ID를 포함할 때만 후보가 된다.
편의점 매뉴얼이 병원·부동산 세션의 근거로 올라오는 것을 막는다.
**업종을 모르거나 `industries`가 비었으면 통과시킨다** — 걸러서 후보가 통째로 비는 쪽이 더 나쁘다는 판단.

### 단계 2. 조항 고정 (`pinned_sections`)  ← **이 시스템의 핵심**

지정된 섹션 안에서만 유사도 검색해 최대 2건을 **결과 맨 앞에 강제로 넣는다.**

왜 필요한가 — 실측 결과:

| 질의 | 별표Ⅱ 식료품 조항의 순위 |
|---|---|
| "식료품 부패 변질 환불 기준" (법률용어) | **1위** |
| "요구르트가 빵빵해졌는데 환불해달라고 합니다" (구어체) | **39위** |
| "유제품이 상했는데 환불" | **168위** |

원인은 두 가지가 겹친 것이다.
① 직원 구어체와 법령 문어체의 어휘 격차,
② 별표Ⅱ에 "제품교환 또는 구입가 환급"만 적힌 비슷한 조항이 업종별로 수십 개라 서로 경쟁한다.

쿼리 확장으로는 해결되지 않았다(문제유형 라벨 추가 → 83위, 법령어휘 확장 → 81위로 **악화**).
그래서 **품목이 사전에 정해지는 경우에는 검색에 맡기지 않는다.**
편의점에서 환불 분쟁이면 품목은 어차피 식료품이므로, 해당 섹션을 직접 지정한다.

### 단계 3. 유사도 검색

후보 풀 `max(top_k*8, 40)`을 뽑아 위에서부터 채운다.

### 단계 4. 문서당 상한 (`MAX_PER_DOCUMENT = 2`)

한 문서가 자리를 독식하지 못하게 막는다.
식품등의 표시기준(249청크)이 "이물질" 질의의 상위 5칸을 전부 차지해서
정작 필요한 매뉴얼·해결기준을 밀어내던 문제를 잡은 것이다.

### 고정 섹션은 어디서 정해지나

파일: [app/graph/recommendation_graph.py](../app/graph/recommendation_graph.py)

```python
PINNED_SECTIONS: dict[tuple[industryId, problemType], tuple[str, ...]] = {
    ("convenience_store", "refund_exchange"):       ("식료품(19개 업종)", "[별표 1]"),
    ("convenience_store", "damage_contamination"):  ("식료품(19개 업종)",),
    ("restaurant_cafe",   "refund_exchange"):       ("식료품(19개 업종)", "[별표 1]"),
}
```

키는 **온보딩에서 고른 업종 + 세션 시작 시 고른 문제 유형**이다.
값은 ingest가 붙인 `section` 문자열의 **일부**면 된다(부분 문자열 매칭).

> **주의**: `"[별표 1]"`은 소비자기본법 시행령 [별표1] 일반기준을 겨냥한 것인데, 그 문서가 지금
> `knowledge-sources/`에 없다(md 전환 때 빠졌다). 매칭되는 청크가 없으니 그 자리는 조용히 비고,
> 식료품 핀만 동작한다. 문서를 다시 넣으면 코드 수정 없이 되살아난다.
> 매칭이 되는지는 ingest 실행 로그의 `[경고] 레지스트리에 있으나 파일이 없음`으로도 드러난다.

## 4. 런타임 — 프롬프트 조립과 출력

### 근거 블록 렌더링 (`_format_knowledge`)

검색된 청크는 이렇게 LLM에게 전달된다:

```
[근거 1] 소비자분쟁해결기준 [별표Ⅰ] 대상품목 · [별표Ⅱ] 품목별 해결기준
  위치: 품목별 해결기준 > 2. 식료품(19개 업종) (p.8)
  종류: 공식 고시(소비자분쟁해결기준)
**청량음료, 과자류, 빙과류, 낙농제품류, ...**
| 분 쟁 유 형 | 해 결 기 준 | 비 고 |
| --- | --- | --- |
| ... | ... | ... |
```

`위치`가 그대로 `citations[].section`이 되고, 문서명이 `citations[].label`이 된다.
`종류`는 `SOURCE_TYPE_LABEL`이 만든다 — 특히 `manual`은 **"사내 실무 매뉴얼(법령 아님)"**으로 찍혀서,
매뉴얼 내용을 법령상 의무처럼 말하지 않게 한다.

### 프롬프트 전체 구조

```
## 상황 정보          업종 / 문제 유형 / 발생 행동 / 이전 조치
## 최근 대화          직전 8턴
## 방금 들어온 발화
## 자동 감지된 위험 표현 (참고 신호, 오탐 가능)   ← 감지됐을 때만
## 근거 문서 후보 (이 안에서만 인용하세요)
```

### SYSTEM_PROMPT의 근거 관련 규칙

- **2번**: 근거 문서 안에서만 답한다. 삼을 내용이 없으면 `citations=[]` + `needsHumanReview=true`.
- **2-1번**: `section`은 근거에 표시된 위치를 **그대로** 옮긴다. 지어내지 않는다.
- **2-2번**: 공식 고시와 사내 매뉴얼을 구분해 말한다("점포 기준으로는", "매장 절차상").

### 출력

`RecommendationDraft`(구조화 출력) → `Recommendation`.
`situation` / `riskLevel` / `confidence` / `sayNow` / `nextActions` / `doNot` / `citations` / `needsHumanReview`.

## 5. RAG를 타지 않는 경로 — 고정 안전 절차

파일: [app/safety/emergency_rules.py](../app/safety/emergency_rules.py), [app/safety/abusive_lexicon.py](../app/safety/abusive_lexicon.py)

위협 키워드가 잡히거나 직전 2턴이 연속 `abuse`/`threat`이면 **생성형을 건너뛰고** 고정 스크립트를 낸다.
검색도 LLM 호출도 없다. 흉기가 감지되면 "즉시 112 신고"가 첫 조치로 올라간다.
citations는 `산업안전보건법 제41조` 하드코딩이다.

> 새 시나리오를 추가할 때, 그 시나리오가 위협 키워드를 포함하면 **RAG 경로로 오지 않는다**는 점에 주의.
> 예: "죽여버린다" 가 들어간 환불 요구는 환불 근거를 검색하지 않고 안전 절차만 나온다. 의도된 동작이다.

## 6. 새 시나리오를 추가할 때 — 체크리스트

### A. 기존 자료로 커버되는 시나리오인 경우 (코드 수정 없음)

그냥 발화를 넣어보고 검색 결과를 확인한다.

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -c "
from app.rag.retrieve import retrieve_relevant_chunks
for d in retrieve_relevant_chunks('새 시나리오 발화', top_k=5, industry_id='convenience_store'):
    m = d.metadata
    print(m['sourceType'], '|', m['documentTitle'][:30], '|', m.get('section'), m.get('page'))
"
```

기대한 조항이 상위에 없으면 → B 또는 C로 간다.

### B. 근거는 있는데 검색이 못 찾는 경우 → 조항 고정 추가

1. 목표 조항의 `section` 문자열을 확인한다(위 스크립트 또는 `build_documents()` 출력).
2. `PINNED_SECTIONS`에 `(업종ID, 문제유형)` 키로 추가한다.
3. 문제 유형이 새로 필요하면 `PROBLEM_TYPE_LABEL`과 프론트엔드 온보딩 옵션에도 같이 추가한다.
4. **재인덱싱 불필요.**

### C. 자료 자체가 없는 경우 → 문서 추가

1. `knowledge-sources/` 아래에 `.md`로 변환해 넣는다(**`.pdf`는 인덱싱되지 않는다**).
   변환 전 원본(PDF 등)을 같이 두려면 `_archive/`에 보관한다(자동 제외).
   변환할 때 **표는 Markdown 표로**, 원문 쪽은 `## 원문 N쪽` 또는 `<!-- 원문 PDF N쪽 -->`로 남긴다.
2. `SOURCE_REGISTRY`에 등록한다 — `title`은 사용자에게 보이는 이름이므로 신중히.
3. `industries`를 정한다. 애매하면 `("*",)`로 넓게 두는 편이 안전하다(가려서 근거가 비는 게 더 나쁨).
4. **임베딩 전에 청크 구성부터 확인한다** (비용 아끼기):
   ```bash
   ./.venv/Scripts/python.exe -c "from app.rag.ingest import build_documents; build_documents()"
   ```
   섹션이 `None`투성이면 변환본에 `#` 헤딩이 없는 것이다 — 코드가 아니라 **변환본을 고친다**
   (PDF 시절과 달리 문서별 정규식 패턴을 추가할 일은 없다).
5. `python -m app.rag.ingest` 실행 (OpenAI 임베딩 비용 발생).
6. `knowledge-sources/README.md`의 인덱싱 정책 표를 갱신한다.
7. B의 검색 확인을 다시 돌린다.

### D. 근거가 아예 없다고 판단되는 경우

그게 정상적인 결과다. 억지로 유사 조항을 끌어오지 말고 `needsHumanReview=true`로 관리자에게 넘긴다.
어떤 항목이 "명시된 자료 없음"인지는 `knowledge-sources/README.md` 하단에 정리해 두었다.
